# Задачи без человека

Модуль `jericho.modules.tasks` выполняет поручения из настроек, когда рядом никого нет: утренняя сводка,
проверка сервера раз в час. Он даёт команду `<проект> task <имя>` и расписание: `<проект> timers install`
ставит по полю `schedule` пользовательские таймеры systemd. Свой планировщик не пишется: systemd уже умеет
календарь, запуск пропущенного после сна (`Persistent=true`), журнал запусков и переживает перезагрузку.

## Подключить

```python
from jericho.core.conf.settings import OutputSettings
from jericho.modules.tasks.settings import ScheduledTask, TasksSettings

class Base(Settings):
    INSTALLED_MODULES: tuple[str, ...] = (..., "jericho.modules.tasks")
    tasks: TasksSettings = TasksSettings(items={
        "morning": ScheduledTask(text="что в календаре на сегодня", schedule="Mon..Fri 08:00"),
        "disk": ScheduledTask(text="сколько места на диске", output=OutputSettings(kind="file", file=Path("~/disk.md"))),
    })
```

Имя задачи пишется строчной латиницей. Ответ уходит в `output` задачи, а если он не задан — туда же, куда
ответы проекта (раздел `output`).

## Что держит код

- Запуск всегда идёт без человека, даже из терминала: команда запускает себя заново с переменной
  `JERICHO_UNATTENDED=1`. Отметку получает и сервер ручек.
- Ручка, которой нужно «да», получает отказ `needs_confirm` с пометкой `nobody`. Вопрос не записывается:
  иначе на него ответило бы «да» из следующей голосовой фразы.
- Вопрос, который ждёт ответа человека, задача не видит и подтвердить не может.
- Задача не попадает в память разговора (модуль `dialogue`).
- Модели к поручению дописано, что переспросить некого. Это подсказка, а не ограничение.
- Неудача даёт код завершения 1, и таймер её видит. В журнале у такой фразы стоит `"unattended": true`.

## Расписание

`schedule` — выражение календаря systemd: `*-*-* 08:00`, `Mon..Fri 09:30`, `hourly`, `*:0/15` (каждые 15 минут).
Проверить выражение: `systemd-analyze calendar "Mon..Fri 08:00"`.

```
<проект> timers install    # поставить таймеры по разделу tasks; после правки раздела — запустить ещё раз
<проект> timers list       # что стоит и когда сработает
<проект> timers remove     # снять все таймеры этого проекта
```

- Таймер ставится только задаче с `schedule`. У задачи, которая пропала или потеряла `schedule`, таймер
  снимается при следующем `install`.
- Файлы лежат в `~/.config/systemd/user/<проект>-task-<имя>.{timer,service}` и помечены первой строкой.
  Чужие файлы не трогаются.
- Неверное выражение останавливает `install` до записи файлов.
- Служба запускает `python -m jericho task <имя>` с переменными проекта: ни PATH, ни оболочка не нужны.
- Ключи API для задач кладут в `~/.config/<проект>/environment` строками `ИМЯ=значение`. Служба читает
  этот файл, если он есть.
- Журнал запусков: `journalctl --user -u <проект>-task-<имя>`.
- Чтобы таймеры работали без входа в систему (на сервере): `loginctl enable-linger $USER`.

## Команды по расписанию

Не всё по расписанию нужно делать моделью. Проверка порогов, уборка, выгрузка — это обычная команда проекта
(своя команда навыка), её ставят в `commands`:

```python
tasks: TasksSettings = TasksSettings(scheduler="cron", commands={
    "watch": ScheduledCommand(command=("watch",), schedule="*/10 * * * *"),   # `<проект> watch` каждые 10 минут
})
```

- Таймер называется `<проект>-command-<имя>`; в файле cron — та же строка, что у задач.
- Команда запускается с отметкой «рядом никого нет» (`JERICHO_UNATTENDED=1`): если она что-то спросит,
  ответить на этот вопрос «да» потом будет нельзя.
- `timers install` и `timers crontab` ставят их вместе с задачами и тиком `due`.

## Отложенные поручения

«Завтра в 9:00 собери сводку», «через полчаса напомни выключить духовку» — поручение ставит сама модель ручкой
`schedule`, а в срок его исполняет команда `<проект> due` без человека рядом, так же как задачу из настроек.

```python
tasks: TasksSettings = TasksSettings(
    deferred=DeferredSettings(enabled=True, output=OutputSettings(kind="notify")),
)
PROMPT_SECTIONS: tuple[str, ...] = (..., "jericho.modules.tasks:prompt.md")
```

После включения — один раз `<проект> timers install` (в контейнере — `timers crontab`): он ставит тик
`<проект>-due` раз в минуту; таймер переживает перезагрузку, повторять установку нужно только после правки
раздела `tasks`. Тик сначала зовёт `python -m jericho.modules.tasks.peek <файл>` — проверку на одной
стандартной библиотеке (`ExecCondition=` у systemd, `if … then` в строке cron), и ассистент собирается, только когда
что-то наступило: пустой тик стоит сотые доли секунды, а не полсекунды.

Два вида:

| Вид | В срок | Модель |
|---|---|---|
| `remind` — напоминание | уведомление с текстом; опоздавшее приходит с пометкой «опоздало на …» | не нужна |
| `do` — поручение | прогон фразы без человека, ответ — в вывод | нужна; опоздавшее больше `grace_minutes` не выполняется (`missed`) |

Ручки: `schedule(kind, text, at)`, `list_scheduled()`, `cancel_scheduled(ids)`.

### Что держит код

- `schedule` — EFFECT, «да» спрашивает сама ручка, и спрашивает всегда. Срок в вопросе называет код
  («завтра, чт 22 октября, 09:00 (через 13 ч)»): человек на слух ловит ошибку перевода «завтра в 9». Срок в
  прошлом, дальше `horizon_days` и сверх `max_pending` отказываются до вопроса.
- Без человека ничего не ставится, даже если проект назвал `schedule` в `unattended_effects`: служба
  подтверждения отвечает `nobody`. Задача не может ставить задачи.
- «Да» при постановке не разрешает действий в срок: ручка с «да» в поручении `do` получит отказ, как у любой
  задачи без человека. Модель предупреждает об этом при постановке.
- Не больше одного раза: поручение отмечается `running` до исполнения, по одному. Упавший запуск его не повторит:
  следующий найдёт `running` и сообщит «исполнение прервалось» (запуски `due` идут по одному, замок `due.lock`, —
  поэтому чужое `running` под замком всегда след упавшего).
- Занят фразой человека — поручение возвращается в ожидание до следующего тика.
- Файл поручений — `<папка состояния>/tasks/deferred.json`, изменения под замком `deferred.lock`. Вхолостую
  поручения живут в памяти, в прогоне `eval` файл стирается перед каждой фразой.

### Настройки `deferred`

| Поле | Смысл | По умолчанию |
|---|---|---|
| `enabled` | включить ручки, `due` и тик | `False` |
| `output` | куда напоминания и итоги; пусто — вывод проекта | — |
| `grace_minutes` | насколько может опоздать `do` | 120 |
| `keep_days` | сколько хранить исполненные | 7 |
| `max_pending` | сколько может ждать сразу | 50 |
| `horizon_days` | дальше этого не ставится | 366 |

Вывод `kind = "notify"` — уведомление на рабочем столе (`notify-send`). Из службы systemd оно дойдёт, только
если у менеджера пользователя есть `DBUS_SESSION_BUS_ADDRESS`: проверить — `systemctl --user show-environment`.
Значок уведомления — `output.icon` (у голоса — `voice.icon`): имя из темы значков (`jericho`) или путь к файлу;
пусто — значок выбирает панель.
